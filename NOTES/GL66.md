# Stela on the MSI Pulse GL66 12UCK (VetTV Studios branch)

Branch `msi-gl66/stela-v0.5-gl66` of `VetTV-Studios/Stela`, a fork of
[tylertms/Stela](https://github.com/tylertms/Stela). Stela's licenses are
unchanged: see `LICENSE`, `NOTICE` and `LICENSES/` (`stela.efi` GPL-2.0-only,
the `stela` CLI GPL-3.0-or-later, Stela's own code GPL-2.0-or-later).

**Status: experimental, untested on GL66 hardware.** Nothing here is known to
fix a GL66 boot. It is upstream `main` (newer than v0.5.0) plus one small,
switchable display change, a read-only link diagnostic, and one opt-in ASPM
switch that is off unless set.

## Target

| Part | GL66 12UCK |
|---|---|
| CPU | Intel Core i5-12450H (Alder Lake, 4P + 4E) |
| Internal panel | 1920x1080, 144 Hz eDP, wired to the Intel UHD `8086:46a3` |
| dGPU | GeForce RTX 3050 Laptop `10de:25a2` (GA107), muxless, no panel output |

Stela has no Intel display driver, so on this laptop macOS is drawn on the
RTX 3050 (nouveau + GSP-RM 570.144 + NVK) and the CPU copies each frame into
the firmware (GOP) framebuffer that the 46A3 scans out: the
"firmware-framebuffer copy" path (`GopScanout::copying_gpu_frames`).

## What this branch changes

### 1. Copy-path refresh cap (experimental, on by default, switchable)

- New `stela.cfg` option: `--copy-refresh-hz HZ` (0 to 480).
  - Not set: the copy path is paced at **60 Hz**.
  - `--copy-refresh-hz 0`: upstream behaviour (the panel's EDID rate, 144.149
    Hz on this class of panel).
  - Any other value caps at that rate.
- It only acts when a bound GPU has no display of its own and its frames are
  copied to the firmware framebuffer. A GPU-driven display (HDMI on the dGPU)
  is unchanged.
- The boot log says so with a line starting with
  `DISPLAY GL66 experimental: copied frames paced at 60000 mHz`.
- The boot log line also gives the frame interval, e.g. `(16666667 ns a frame)`.
- Code: `crates/stela-boot-core/src/options.rs` (+ `parse.rs`, `error.rs`,
  `tests.rs`), `crates/stela-boot-core/src/copy_refresh.rs` (the pacing and
  frame-interval math, with unit tests in `copy_refresh/tests.rs`),
  `crates/stela-boot/src/engine/display.rs`,
  `crates/stela-boot/src/engine/start.rs`.

Why: the DCP model advertises the scanout's refresh to macOS and paces
WindowServer by it. On the copy path that refresh is the panel's EDID rate.
The #197 log (Acer A715-76G: same i5-12450H, same 46A3 muxless panel, GA107 RTX
2050) shows `DISPLAY EDID (active) prefers 1920x1080 at 144.149 Hz`. It also
shows `copied to the firmware's framebuffer ... at 1920x1080, 144149 mHz` and
the freeze after Language Chooser. #203 (copy path, 165 Hz panel) reports a
sluggish desktop. At 144 Hz, one CPU may copy each changed row up to 144 times
a second into uncached/write-combined iGPU memory. 60 Hz is the rate
`Advertised::of_monitor` already falls back to when a refresh cannot be
advertised (`crates/stela-soc/src/dcp/iomfb.rs`), so it is a path macOS
already takes.

Honest limits: this lowers CPU copy load and pacing pressure. Nothing shows
that load causes #197's GPU loss or #186's black screen. It is a cheap A/B
knob, not a fix.

### 2. PCIe link diagnostic for the dGPU (read-only, always on)

At GPU claim, the boot log gets two lines, one for the GPU's end of the link
and one for the port (PCIe root port) above it:

```
GPU 0000:01:00.0 GL66 diagnostic: PCIe link control 0x.... (ASPM L0s=. L1=.) link speed genN
GPU 0000:01:00.0 GL66 diagnostic: port 0000:00:01.0 PCIe link control 0x.... (ASPM L0s=. L1=.)
```

Nothing is written. Both words are read after the GPU was brought to D0. If
firmware left the GPU in D3hot (the log then also has `firmware left it in
D3`), that D0 entry may reset the GPU's own word, so the port's word is the
one that shows firmware's setting. L0s is per direction, so the port's L0s
alone matters; L1 needs both ends. A GPU without a PCIe capability logs
`PCIe link control: none` instead of a fake `0x0000 ... gen0`.
Code: `crates/stela-boot/src/engine/gpu.rs` (`claim`), the port read in
`crates/stela-boot/src/native_mmio/shared/config_space/containment/gl66_aspm.rs`.

Why: in #197 the GPU starts answering MMIO with all ones mid-session
(`timer: stalled at ffffffffffffffff`, then `gsp: no answer ... in 30000 ms`
and `VK_ERROR_DEVICE_LOST`). That means the GPU dropped off the bus or lost
power, so longer GSP timeouts cannot help. Firmware-enabled ASPM L1 on a
muxless dGPU link is one known cause of that on Linux. Stela's logs do not say
whether firmware left ASPM on. These lines do, and decide whether to try the
`--gl66-aspm-off` switch below.

### 3. `--gl66-aspm-off` (experimental, off unless set)

- New `stela.cfg` flag: `--gl66-aspm-off`. Not set: nothing changes.
- When set, at GPU claim (before nouveau binds and before GSP-RM boots),
  ASPM L0s and L1 are cleared in the Link Control of the GPU and then of the
  port above it, the order Linux uses to disable ASPM. Both capabilities are
  checked before either is written; each write is a 16-bit write of Link
  Control only (Link Status's write-one-to-clear bits are untouched), and
  each is read back. Other Link Control bits are kept. Nothing is ever turned
  back on; a refusal is logged and the GPU still starts.
- Log lines, right after the diagnostic ones:

```
GPU 0000:01:00.0 GL66 experimental: --gl66-aspm-off: PCIe link control 0x0042 -> 0x0040 (ASPM L0s=0 L1=1 -> L0s=0 L1=0)
GPU 0000:01:00.0 GL66 experimental: --gl66-aspm-off: port 0000:00:01.0 link control 0x0042 -> 0x0040 (...)
```

  or `--gl66-aspm-off refused: ...` with the reason.
- It applies to every GPU Stela claims, not only the GL66's, so leave it off
  on other machines.
- Code: `crates/stela-driver-base/src/bus/pci/aspm.rs`
  (`disable_aspm_device_and_port`, with unit tests in `aspm/tests.rs`),
  `crates/stela-boot/src/native_mmio/shared/config_space/containment/gl66_aspm.rs`
  (finds the original forwarding bridge above the GPU and rechecks its
  forwarding after), `crates/stela-drivers/src/probe/services.rs` and
  `crates/stela-boot/src/engine/services.rs` (the service hook),
  `crates/stela-boot/src/engine/gpu.rs` and `start.rs` (the call),
  `crates/stela-boot-core/src/options.rs` (+ `parse.rs`, `error.rs`).

**When to try it:** only if the first boot log's diagnostic lines show
`L0s=1` or `L1=1` on the GPU or on its port. If both show `L0s=0 L1=0`,
firmware already has ASPM off and this switch would change nothing.

Why it is opt-in: L1 on a muxless dGPU link is a known cause of a GPU
dropping off the bus on Linux, but nothing yet shows it is the cause of #197.
Turning ASPM off costs some battery and is otherwise harmless; it is not a
fix until a log says so.

### Considered and not changed

- **25A2 device ID / quirks.** Not needed. #186's v0.5.0 log on the same
  `10de:25a2` shows `NVIDIA GA107 (b77000a1)`, `gsp: RM version: 570.144`,
  `nouveau bound it`, and VRAM 4096 MiB.
- **Longer GSP timeouts.** Rejected. #197's MMIO reads return all ones, so the
  GPU is gone, not slow. Upstream `0218` already ends those waits at once and
  logs PCI state.
- **`OPTIONS_REVISION` bump** (`crates/stela-loader/src/mount_interface.rs`).
  Not bumped, on purpose. Its rule is a bump when an option changes meaning
  or a *required* one is added. Both of our options are optional, setup never
  writes them, and an unset one prints nothing, so a stick made by either CLI
  reads the same. Bumping would only make the official CLI refuse our sticks.
  The catch is the other way round: stock `stela.efi` refuses a `stela.cfg`
  line that still holds one of our options (see the fallback below).
- **A lower bound for `--copy-refresh-hz`.** Values 1 to 59 are accepted, as
  any opt-in value is. A rate the DCP model cannot advertise falls back to
  60 Hz (`Advertised::of_monitor`); a low one it can advertise just makes the
  desktop slow. Use 0, 60 or 72.
- **`GPU CLIENT FAULT` lines (#186).** Not a bug by themselves. They are served
  demand faults on GPU client mappings (`serve_moved` in
  `crates/stela-boot/src/engine/gpu/client.rs`), logged at powers of two. A
  desktop RTX 3060 Ti reached the desktop with `count=64`. #186's black screen
  is on an HDMI output driven by the dGPU, which the GL66 test does not use.

## Build (Linux)

Needs Rust (rustup; `rust-toolchain.toml` pins 1.99.1), git, Python 3.10+,
LLVM/Clang/LLD/libclang 21 and the C++ standard library headers
(`libstdc++-dev`).

```sh
git clone -b msi-gl66/stela-v0.5-gl66 https://github.com/VetTV-Studios/Stela
cd Stela
export PATH=/path/to/llvm-21/bin:$PATH LIBCLANG_PATH=/path/to/llvm-21/lib
cargo xtask dist        # about 15 min on 8 cores the first time
cargo test -p stela-cli -p stela-boot-core -p stela-driver-base --lib
```

Outputs: `target/release/stela` (Linux CLI with `stela.efi` embedded) and
`target/boot/x86_64-unknown-uefi/release/stela-dist.efi`.

A Linux build has no `Stela.app` (it is built on a Mac). The kext logs
`Stela.app: no package` and installs no helper app. The official v0.5.0
release embeds it. Nothing in the boot path depends on it.

## Test plan (only with Vet's go)

Hard rules: a **spare** USB stick for Stela, and (if installing) a **separate
spare disk** of 60 GB or more. **Never the internal drives** (Micron / the new
1 TB) and **never the 256 GB Sequoia/NullMoth drive**. Unplug that drive
before starting. Use USB Ethernet (README list: RTL8152/8153/8156, AX88179,
AX88178A, AX88772, CDC ECM/NCM). Do not rely on Wi-Fi.

1. Photograph the BIOS settings (Secure Boot, boot order, anything else).
2. Plug in only the spare stick (and, if used, the spare target disk).
   - **Windows (preferred):** open Terminal **as administrator** in the
     `gl66-windows` folder, check the hash, and run `.\stela.exe`. Choose the
     spare stick and the installer, then confirm. This erases the stick.
     Check the stick's name and size in Disk Management first.
   - **Linux:** check names with `lsblk -o NAME,SIZE,MODEL,SERIAL`, then run
     `sudo ./stela` from `gl66-linux-ci`.
3. Optional A/B: on the stick's EFI partition, `EFI/stela/stela.cfg` is one
   line starting with `--system`. Append ` --copy-refresh-hz 0` to get
   upstream pacing. Leave it off for the GL66 default (60 Hz). `stela update`
   rewrites this file, so add it again after an update.
   - Leave `--gl66-aspm-off` **off for the first boot.** Add
     ` --gl66-aspm-off` to that line for a second boot only if the first
     log's `GL66 diagnostic` lines show `L0s=1` or `L1=1` on the GPU or its
     port. Change one option per boot so the logs compare.
4. Power off. Turn Secure Boot off and keep UEFI. Plug in the USB Ethernet
   adapter and AC power. Boot the stick from the boot menu.
5. Install only to the spare target disk. Go through Language Chooser and
   Setup Assistant. Note the time (CT) of anything odd, and photograph any
   `STELA FATAL` / `STELA STOPPED` screen.
6. After each boot (good or bad), back in Windows (Terminal as administrator):
   `.\stela.exe log --output gl66-<date>-<n>.txt`. On Linux:
   `sudo ./stela log --output ...`. The log's `STELA UEFI MOUNT version=` line
   should read `0.5.0-vettv.gl66.2`.
7. Restore: power off, unplug the stick and the spare disk, turn Secure Boot
   back on, and restore the boot order. Check that the normal boot is back
   before reconnecting the 256 GB drive.

### What to look for in the log

- `DISPLAY EDID (active) prefers ...` and `DISPLAY no GPU output has a display`:
  confirms the copy path.
- `DISPLAY GL66 experimental: copied frames paced at ...`: confirms our cap.
- `GPU 0000:01:00.0 GL66 diagnostic: PCIe link control ...` and
  `... GL66 diagnostic: port ...`: the ASPM state at both ends of the link.
- With `--gl66-aspm-off`: `GL66 experimental: --gl66-aspm-off: ...` with each
  word before and after (both should end `L0s=0 L1=0`), or `refused`.
- `nouveau ... NVIDIA GA107`, `gsp: RM version`, `nouveau bound it`.
- `DCP PACING ... presented=... per_second=... fence_timeouts=...`:
  smoothness.
- Failures: `timer: stalled at ffffffffffffffff`, `gsp: no answer`,
  `VK_ERROR_DEVICE_LOST`, and upstream 0218's one-time line about what the
  GPU's PCI configuration still answers.

Redact MAC addresses, disk serials, host name and any Apple ID before sharing
a log.

## Fall back to stock v0.5.0

- The surest way: re-make the spare stick with the official `stela.exe` from
  Vet's verified zip (`stela-v0.5.0-windows-x86_64.zip`, sha256
  `cfc59590d9b4a7ccaef8ee53c270eb94108855924f7c37d235a74b69b6e378f5`, matches
  the release's `SHA256SUMS`). This erases the stick again.
- Or, in Terminal as administrator with the stick plugged in, run the
  official `.\stela.exe update`. It replaces the loader because the
  `stela.efi` hash differs, and the versions compare as equal, so it does not
  refuse. Check that the next boot log reads `version=0.5.0`.
- `update` (ours or the official one) rewrites `EFI/stela/stela.cfg` from the
  stick's record, which drops a hand-added `--copy-refresh-hz` or
  `--gl66-aspm-off`. The stock parser knows neither option, so make sure both
  are gone before booting stock `stela.efi`.
- A macOS already installed on the spare disk is left as it is.
